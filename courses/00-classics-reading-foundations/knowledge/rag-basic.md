# 基础 RAG：先找资料，再组织回答

想象读者问“第一讲怎样解释序言与日记的差别”。程序先找到相关讲稿片段，再把片段、来源与问题交给模型。答案生成后，还要能回到这些片段核对。

## 拆成准备资料与回答问题两段

准备时：读取文件 → 保留来源 → 切分片段 → 建立可查询的索引。

回答时：接收问题 → 检索相关片段 → 将片段放入请求 → 生成回答 → 核对引用。

常见向量方案使用 Embedding 表示问题与片段，再按相似性取候选；“先检索、后生成”的固定流程并不要求所有实现都使用向量数据库。[LangChain 检索文档](https://docs.langchain.com/oss/python/deepagents/retrieval)介绍了这些组件和固定流程。

## 放回这五份讲稿里理解

目前 JSON 中每讲只有一个长段落。它适合验证有没有读漏正文，却未必适合直接作为检索单位。后续可以切出小块，但每块仍需保留讲次、文件名和原文位置。

“第一讲”是元数据限制；“序言与日记的差别”是内容线索。二者一起用，比把所有讲稿混在一起然后要求模型猜来源更容易检查。这是本项目后续实验的设计思路，效果仍须用题单验证。

## 常见误解

| 说法 | 应怎样核对 |
|---|---|
| 有向量库就算有 RAG | 检索结果是否真的进入生成请求？ |
| 引用了文件名，答案就有依据 | 引用内容是否支持这句话？ |
| RAG 会消除模型幻觉 | 仍可能检索错误、漏资料或生成无据结论 |
