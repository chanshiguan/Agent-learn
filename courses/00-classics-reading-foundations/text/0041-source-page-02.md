### 第 1 步：让 API 返回你刚写出的页面

使用与代码相邻的 web 目录，避免启动目录变化导致找错文件。

**写在哪里：**项目根目录下的 `companion/basic_app.py`。 在文件末尾另起一行，接着写下面这一段；已有内容保留。

**先理解：**`@app` 装饰器把函数登记为接口。路径决定请求去哪，函数参数决定请求怎样验证；只定义函数不会向模型发请求。

```python
# 目的：使用与代码相邻的 web 目录，避免启动目录变化导致找错文件。
# 预期：GET / 返回页面，页面继续调用同源 /api/ask。
@app.get("/")
def index():
    return FileResponse(Path(__file__).with_name("web") / "basic.html")
```

**写完后应当怎样：**GET / 返回页面，页面继续调用同源 /api/ask。

## 页面不是把 JSON 原样贴出来

学生想知道答案，家长想核对依据。因此先展示回答，再把来源作为可展开内容。来源显示文件名、段落和片段，不用内部服务地址来增加读者负担。复杂调试信息留给开发记录。

打开 `companion/web/basic.html`，看提交事件如何改变按钮与状态文字。页面用 `textContent` 显示讲稿和模型输出，不把未知文本当 HTML 执行。这既保留原文，也避免把一段带标签的回答变成页面脚本。

## 做三种真实操作

1. 提交一个有依据的问题，展开来源，在 DOCX 找到同一段。
2. 提交版本页码问题，检查不足提示是否清楚，并避免显示上一题来源。
3. 连续点击提交，观察等待期间按钮是否阻止重复请求。浏览器开发工具的 Network 中应能看到一次 POST 和对应状态。

用窄窗口再看一次：输入、按钮、来源能否按顺序阅读，长文件名是否挤出屏幕。用 Tab 移动焦点，不使用鼠标完成一次提交。这些检查也是后面真实产品验收的一部分。

**为什么不直接 innerHTML 显示答案？**

模型和讲稿文本都不是可信页面代码。textContent 按文字显示，避免意外执行标签或脚本。

**来源区至少应让读者完成什么？**

知道答案用了哪份资料，并能回查具体文字；只有一个无法打开的编号还不够。

**通过证据：**一份界面检查记录，覆盖有据、无答案、失败、窄屏与键盘操作。
