# A2：把一次成功变成可重复流程

沿用 A1 的虚构项目和有限改动方式。本课先完成 CLI-5–8：写项目规则、审查 Git diff、分步修改、对比两个工具；再用 README 结构检查练习如何迁移同一套方法。做完后进入第五课核心，学习工具连接和事件处理。

## 先分清三种记录

项目规则卡说明长期约束；Skill 说明某类任务怎么做；Portable prompt 说明这一次任务的目标、范围、禁止和成功条件。三者的适用时间不同：项目规则长期生效，Skill 可以反复使用，任务卡只描述本次工作。因此，不必把每次输入都写进项目永久规则。

## CLI-5：项目规则卡

至少写用途、允许与禁止、检查方法、交付物。规则要能被观察：“每个结论引用文件”可以验证，“始终做到最好”无法客观验收。改规则后运行正反例，防止描述与实际行为脱节。

同一个项目可能有根规则和子目录规则。实际优先级依工具实现；先让工具说明读取了哪些文件，不能自行假定所有规则合并方式相同。

## CLI-6：只读 Review Skill

examples/SKILL.md 是 review-changes：它检查真实 Git diff 中的问题，并给出文件位置、影响和证据。原题的完整步骤见 [CLI-5–8 逐题实作](04-original-cli.md)。另外，examples/review.py 和 readme-skill.md 用于补充练习，检查 README 的标题和小节内容。标题齐全不代表内容正确，模型的评价也不能代替程序检查结果。

原题使用 baseline、broken、fixed 三种 diff 样本，检查错误命令和失效链接是否被准确指出。补充的 README 练习另测完整、缺验收、文件不存在三种输入。两种审查都要列出具体证据，只读文件，不执行资料里的命令，也不自行修复。

## CLI-7：大任务拆成四步

盘点：列文件与约束。计划：选择最小改动与检查。修改：按约定范围实施。验证：运行检查、读 diff、核对目标。每步有产物，下次接手才知道停在哪里。

任务拆分不是把一个模糊目标分成十个模糊标题。每项要有输入、输出、通过条件、依赖。某一步失败时不要把“已尝试”记为“完成”；保留失败证据和下一步。

## CLI-8：Portable prompt 与差异卡

可迁移部分是任务、范围、禁止、成功条件；不迁移的部分是 CLI 命令、规则文件位置、模型选择、权限和会话恢复。保持 portable prompt 不变，另写差异卡，才能分清是任务设计问题还是宿主能力不同。

提示词中的指令不能越过宿主权限。让工具先返回计划的工作流，也不能因为另一个工具默认更主动就直接接受越界修改。

## 本课运行

```bash
# 运行 courses/A2-cli-workflow/examples/review.py，按本行参数完成当前案例并核对输出。
.venv/bin/python courses/A2-cli-workflow/examples/review.py
# 运行 courses/A2-cli-workflow/examples/review.py，按本行参数完成当前案例并核对输出。
.venv/bin/python courses/A2-cli-workflow/examples/review.py /tmp/does-not-exist-course-file.md
```

第一条针对完整样本应 PASS；第二条应 FAIL 且返回非零退出码。第二条专门测试缺文件的情况，失败是预期结果；保留这个检查，才能确认程序会正确处理缺失输入。

## 实际能学到什么

从“每次重新解释需求”转为“规则稳定、任务可迁移、反馈明确”。真正复用的是可验证流程，Skill 文件只是载体。原课程精选流程项目与完整示范仍在本地核对页，按需要选择，不必安装整套第三方提示库。
