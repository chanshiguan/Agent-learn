第四课解决流程怎么走，第五课解决工具与工作环境怎么连接。这一课补上资料从哪里来、哪些信息可以留到下一次。先读概念和原练习所需知识，完成向量、资料库、切分、RAG、记忆五个小实验；再做综合助手，最后学习进阶方法并运行 A/B/C 对照。受管云检索是选修，不影响本地学习顺序。

一课两种能力

主线必读

RAG 是先检索外部资料，再让模型依据资料回答；Memory 是把未来仍需要的状态保存下来，再在适当时候取回。聊天历史是发生过的记录，context 是当前请求看见的内容，二者都不自动等于可靠记忆。RAG 和普通应用记忆一般不改变模型权重。

本课先完成原练习 1–4 的检索管线，再完成练习 5 与持久记忆补充。最后做一个能给出处、能承认无证据、能记住并删除回答偏好的助手。

1. 什么情况下用什么

主线必读
情况 起点 需要验证
只有几页资料，本次用完 直接放入 context 长度、遗漏、引用
多份资料，问题不同会用到不同段落 RAG 找到正确片段且答案受支持
下次还要记得偏好或任务状态 Memory 授权、隔离、更新、删除
希望稳定改变模型行为 微调等训练方法 数据质量、泛化与评测

向量库不是 RAG 的必要条件。结构化账目优先 SQL，产品编号可能适合字词检索，文档语义相似才适合 embedding。先看资料是什么类型、需要怎样查询，再选择工具库。

2. Embedding 与相似度

主线必读

Embedding 模型把文本转成固定维度的浮点向量。向量本身不是可读摘要，也不是加密。把文档和问题用相容的模型映射到同一空间，才能比较距离；更换模型或维度通常需要重建索引。

余弦相似度是两向量点积除以长度乘积，比较方向；不能把相似度 0.8 解释成“答案正确概率 80%”。余弦不适用于零向量；某些数据库返回 distance，越小越相近，不要把排序方向弄反。

原练习 1 的完整程序在 examples/upstream/01-embeddings，使用真实 embedding 模型；首次运行可能下载模型。固定数字向量只适合验证计算，不能证明语义模型有效。用“同义句、同主题但否定、完全无关句”三类对照，比只测两个相近句更有信息。

3. 两条流水线

主线必读

索引：读取 → 清洗 → 切片 → 嵌入 → 保存文本、向量和来源。

查询：问题 → 权限过滤 → 检索候选 → 可选重排 → 提供证据 → 生成 → 检查引用。

每个 chunk 至少应保存 doc_id、chunk_id、来源位置、版本、权限范围。文档更新后要使旧索引失效或明确版本；否则模型可能引用过期条款。先过滤可见资料，再排序，不要先取出他人资料再让模型“别说出来”。

4. 切片不是越小越好

主线必读

固定长度最简单，但可能把定义和例外切开。Overlap 让边界内容有重复，减少断句损失，也会增加索引和上下文成本。段落切分保留自然语义；Markdown 标题切分利用结构，但不等同于基于语义模型判断断点的 semantic chunking。

过小：命中一个词却丢了限定条件。过大：检索命中后带入太多不相关内容，占据 context。可用 parent-child：小块检索命中后带回相应大段。没有通用最佳 chunk_size，中文字符、英文词和 token 不是同一个计量单位。

原练习 3 同时展示固定长度、段落、标题三种方法。固定同一组问题，比较片段数、平均大小、来源完整性、Recall@k 与最终答案；只看“生成了多少块”不足以决定方案。

5. Chroma 与完整 RAG

主线必读

Collection 管理一组相容的向量与记录。add 用于新 ID，upsert 用于新增或更新；重复 ID、维度不一致要处理。Client 的临时数据不等于长期存储；PersistentClient 才把数据写到指定目录。默认 embedding 功能可能自动下载模型，应在准备阶段说明。

原练习 2 在 examples/upstream/02-vector-db；练习 4 在 04-full-rag-pipeline。查询返回的 ID、文本和 metadata 要一起交给答案生成。提示中要求“只根据这些资料，有缺口就说明”，再在程序中检查引用 ID 是否属于本次候选。

有引用还不够，还要看它是否支持当前说法：资料写“工作日处理”不能支持“周末也能处理”。检查时把回答中的每个判断与原文逐条对照，尤其注意数字、日期、否定词和适用对象。工具结果中的“忽略之前规则”仍是资料，不应成为指令。

7. 检索差在哪里，才加哪一种技术

主线必读

检索先从资料库中挑出一组可能有用的段落，称为候选。可以从两种方法理解候选怎么找。关键词检索会比较问题和段落里出现了哪些词；向量检索会把问题和段落分别转换成向量，再按语义相似度查找。这里的“语义相似”有助于找到同义表达，但不保证段落真的回答了问题。

BM25（Best Matching 25）是一种常见的关键词检索算法。它会看问题中的词是否出现在段落里，出现几次，以及这些词在整批资料中是否少见；也会考虑段落长度，避免长段落仅凭包含更多词而占优。因此，BM25 往往能找回产品代码、专有名词和精确短语。它主要匹配词面，资料若用问题里没有出现的同义说法，可能找不到。向量检索（dense retrieval）通常能弥补同义表达上的差距，但对产品代码等精确词面未必可靠。改写查询就是把原问题换成保留原意的常见说法，再检索一次。

同义表达漏检时，可先试向量检索或查询改写；产品代码漏检时，检查关键词检索，或加入 BM25。Hybrid Search（混合检索）从关键词检索和向量检索两路取回候选，再合并排序。两路系统的原始分数含义和范围可能不同，直接相加未必合理。RRF（Reciprocal Rank Fusion，倒数排名融合）只比较排名：某段落在一路排第几，就为融合分数贡献 1/(k+排名)；它在不同列表出现多次，贡献就累加。程序中的 k 是平滑影响的常数，本例用 60。

examples/ranking_lab.py 用固定的两组排名演示 RRF 与指标怎么算，不调用 embedding 模型，因此只验证“如何合并给定排名”，不验证向量检索本身是否能找到相关段落。

如果正确段落已在候选里、只是排得太低，可以用 Reranker（重排器），让它把问题与各候选段落配对后重新评分。它不能找回未进入候选的段落。因此先检查 candidate recall@k（前 k 个候选找回的正确段落占全部正确段落的比例），再判断重排是否有效。跨文档关系难以直接命中时，再考虑图检索或多步检索；候选已有正确证据而答案仍出错时，应检查生成和引用验收。

注意，Hybrid Search 是“关键词与向量两路找资料并合并排序”。Hybrid RAG 是把固定检索步骤与 Agent 决策结合的流程结构。它们都带有 Hybrid 一词，指的却不是同一件事。

8. 查询、图与反思型检索

主线必读

Multi-query 生成多种表达；Decomposition 把复合问题拆开；HyDE 先生成假想答案帮助检索，假想答案本身不能当证据；RAG Fusion 合并多查询的排名。限制查询数与循环数，防止不断改写却没找到新资料。

GraphRAG 从资料抽取实体关系和社区主题，适合跨文档关系或整体主题问题；构图成本更高，错关系也会传播。LightRAG 是另一实现，不是 GraphRAG 的别名。问题只需一段原文时，先保持简单检索。

Self-RAG 原方法包含训练出的反思 token，不等于普通 Prompt 加“反思一下”。CRAG 评估检索是否可靠，按正确、错误、不明确分支精炼或补找资料。Adaptive-RAG 根据复杂度决定不查、查一次还是多步查。教学中的 if/else 可以演示如何选择处理分支，但没有复现原论文的训练过程，也不能用来验证论文结果。

RAPTOR 对文本聚类、摘要并递归形成树，支持不同层级检索；其降维、软聚类与查询方式有具体设计，手工按章节做摘要树只是示意。DSPy 把任务写成模块、输入输出约定和指标，用样本优化提示或示例；训练/开发/测试要分开，不能用保留题反复调参。

9. Memory 的生命周期

主线必读

先提出保存候选 → 检查是否必要且允许 → 规范化 → 保存 owner、source、时间、版本、期限 → 在相同用户与任务范围内检索 → 更新冲突 → 删除或过期。

短期/长期说的是作用范围；把所有聊天写进硬盘不意味着设计好了长期记忆。Semantic 是事实或偏好，Episodic 是经历，Procedural 是步骤规则；semantic memory 与 semantic search 不是同义词。

原练习 5 使用 Chroma PersistentClient，已有磁盘保存和跨进程读取测试。补充 examples/memory_store.py 使用 SQLite，进一步演示授权、隔离、版本冲突、期限与删除。身份 owner 在教学调用中直接传入；生产要由登录态提供，不能允许模型通过填写别人的 owner 来取得访问权限。

删除主表后仍可能存在缓存、向量索引、备份或日志，本例只保证当前 SQLite 业务行不再返回，不保证磁盘取证级擦除。过期后不再检索与实际清理存储也是两件事。不要把“我忘了”当删除证据。
