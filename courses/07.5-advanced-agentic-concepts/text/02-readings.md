# 第 7.5 课的阅读整合

## Harness Engineering

人的工作转向定义目标、环境和反馈，而不是仅逐行写实现。仓库中的版本化文档应成为可核查记录；短规则文件提供地图，深入说明在对应目录。文档会过时，需要检查更新，不应把旧说明当事实。

架构约束可通过依赖规则、lint、测试和构建落实。让 Agent 能运行并观察应用，有助于把“看起来合理”转成可复现证据。自主完成需要反馈和恢复设施，不是把一句“不要问我”写得更强硬。

## Building Effective Agents

先用最简单的流程结构；只在任务确实需要时增加 chaining、routing、parallel、orchestrator-workers 或 evaluator-optimizer。每一种模式都付出额外 token、延迟和调试成本。工具设计要清晰，环境观察要真实，循环要能终止。

## Eval 与基础设施噪声

同一个模型可能因时间限制、机器资源或并发策略改变而得分不同。记录 harness commit、工具、环境、超时、评分器和次数；环境错误单列。Holdout 不用于优化；Judge 用人工样本校准；读失败轨迹才能看见高分掩盖的问题。

## 长期任务、研究系统与复杂度反例

长期编码工作先建立启动与验证脚本、特性清单、进度记录；每次接手先确认现状，再做一件可验收事。上下文压缩不是自动可靠的交班机制。

多 Agent 研究可通过独立搜索增加广度，但需要明确任务边界、来源质量和合并方式。紧密共享上下文的任务可能因为分散而变差。实际事故说明口头禁止不足以阻止越权，控制必须落到权限和执行器；不能用单次事故推导所有同类产品都不可靠。

The Bitter Lesson 讨论通用计算与学习方法的长期趋势，不是直接制定 Agent 删除清单。教材核查时未能打开原站，因此这里仅说明原课程引用的观点及其适用范围，没有核读原文全文。官方长任务案例里的比例和成本来自特定系统，不是推荐你机械照抄的常数。

## Dynamic Workflows

可读脚本把任务拆分、并行和收集过程保存下来，便于观察和重跑。运行中的交互方式、暂停和恢复与普通聊天不同；仍要设置权限、并发、总量和失败处理。它不是新的模型，也不是所有工作流引擎的替代品。具体用法在第五课的本地资料中对应学习。
