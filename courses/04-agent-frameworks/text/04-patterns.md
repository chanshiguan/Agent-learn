# 五种流程与工具接口：从文章概念到可执行模型

## 为什么不是每项任务都需要 Agent

一次调用已有足够信息且答案能验收时，增加循环只增加费用和不确定性。需要动态探索时才让模型选择下一步。先记录单步方案在哪些题上失败，再判断是缺少处理步骤，还是缺少资料。仅凭模型建议“增加代理”，还不足以决定改架构。

增强模型通常接检索、工具和记忆：检索补当前证据，工具改变或观察环境，记忆延续有价值状态。它们不能相互代替。工具输出要明确“没找到”“执行失败”“已成功”的区别，避免模型把空字符串当成功。

## 五种模式怎样选择

| 模式 | 输入输出关系 | 合适问题 | 停止与失败 |
|---|---|---|---|
| 链式 | 前一步产物作为下一步输入 | 先提纲再正文再检查 | 中间检查不通过就停止 |
| 路由 | 类别决定处理器 | 格式审查与事实审查分流 | 未知类别澄清，不硬猜 |
| 并行 | 独立分支后合并 | 同一稿件的格式和来源检查 | 分支失败单列，不能只合并成功项 |
| 编排者与工作者 | 按任务动态分解工作清单 | 输入规模不同的资料研究 | 控制总任务数、重复与合并责任 |
| 评价与改进 | 产物→明确反馈→修订 | 能给出可验证改进标准的草稿 | 轮数有上限，保留更好版本 |

并行还可分成分片处理和投票判断。投票只能提高某些条件下的稳定性，几个模型可能共享同一偏差。动态工作者也不等于无限递归：任务边界、工具权限和失败上报要在委派前明确。

## 从模式到框架 API

LangGraph 的 node 是函数，edge 是控制关系，state 是共享字段，compile 生成执行对象，invoke 运行。静态顺序用 add_edge，分支用 add_conditional_edges，动态工作者需要明确每个工作者的输入；并行输出通过 reducer 或独立字段合并。checkpoint 保存运行位置；store 存跨会话信息。这些 API 的用法见[动态分工与交接](06-framework-apis.md)；学完后，在[综合摘要流程](03-workshop.md)中练习持久化和跨进程恢复。

OpenAI Agents SDK 中，主管将专家包装为工具，收到结果后仍由主管回答；handoff 则让接收 Agent 继续。接收方接管后，不保证主管会立即回来总结；这与主管把专家当工具调用的流程不同。代码编排可以和模型选择混合：例如代码强制先检索，模型只在有限候选工具中选一个。

CrewAI 的 Agent 定义角色、目标和工具，Task 定义任务及预期产物，Crew 安排合作；Flow 处理应用级事件和状态。角色描述不能代替真实资料传递。研究者给写作者的至少包括结论、原证据和未确认项，审查者需要看到同一份证据，才能判定是否编造。

## 两个应用域与工具设计

客服场景的关键不是“语气像客服”，而是能读取订单事实、知道何时升级人工、执行前确认具体变更。编码场景要能查看文件、运行测试并观察外部结果，测试失败时不能以自然语言宣布完成。两者都需要明确停止点，难题应交人而不是无限循环。

工具说明写清适用情况、输入单位、输出结构和错误含义。例如发生 timeout 时，返回 error 与 retryable，让调用者知道请求失败，而不是返回空搜索结果；文件工具使用明确路径，避免相对目录猜测。先用少量真实输入观察错误，再修改工具定义。不要通过提示词要求工具具有它没有的权限。

## 参考观点的边界与本地自测

多 Agent 研究适合可分开的广度探索；紧密共享上下文的任务容易因摘要和分工丢约束。AutoGen、CAMEL、ChatDev 和社会模拟研究提供不同消息、角色及协作组织方法，不能据其存在推断你的项目需要多个角色。比较时记录质量、成本、延迟及失败类型，研究论文中的改善比例不是本项目预计收益。

自测：并行来源检查失败而格式检查通过，整体能通过吗？不能，两项检查必须同时通过。为什么 optimizer 不应只收到“再好一点”？因为没有可观察差距，无法判断修订有没有收益。为什么一个节点里加三个角色名不算三个 Agent？因为没有独立的状态、调用与交接行为。
