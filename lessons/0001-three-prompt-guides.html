2. 三家真正共同的底层逻辑

三家的 API 名称和示例不同，但都在强调同一个循环：

定义成功→写清任务→补资料/范例→固定测试→一次改一处
好结果 ≠ 好听的 Prompt
好结果 = 任务清晰 × 资料足够 × 模型能力 × 可验证流程

共识一：指令和资料不是一回事

“将客服留言分类”是指令；“我被扣款两次”是这次要处理的资料。把它们分开，程序才能只替换资料而保持任务不变。

共识二：范例不是知识，是行为演示

Few-Shot 不是在训练模型参数。它是在当前请求中告诉模型：“这种输入，我期望这种输出。”范例最有价值的地方是展示边界和格式。

共识三：上下文不足，改句式没用

如果模型不知道你公司的退款政策，把“请认真回答”改成“请非常认真地回答”不会创造政策内容。必须把可信资料放进上下文，或让模型调用查询工具。

共识四：只有 Eval 能说明“变好了”

看到一次漂亮回答，只能证明这次回答不错。要比较两个 Prompt，必须使用同一模型、同一参数、同一测试集和同一评分标准。

3. Anthropic：用一系列小实验建立手感

Anthropic 的交互式教程有 9 章和附录，包括基本结构、清晰直接的指令、角色、数据与指令分隔、输出格式、分步处理、Few-Shot、幻觉和复杂 Prompt。它的核心价值是用小实验观察 Prompt 如何改变模型行为。本项目已将这些实验目标改写成中文示例和页底测验。

第 1 章真正在教什么

  • model：选择哪个模型，它决定了能力、速度和成本的上限。
  • max_tokens：生成上限，是硬停止。设得太小会在答案完成前截断。
  • messages：保存对话轮次，每条消息有角色和内容。
  • system：放稳定的高层行为指导，与当次用户输入分开。
  • temperature：影响采样随机性；教程用 0 来减少练习中的随机干扰。

教程还用错误消息结构演示 API 为什么报错，并用自动评分练习让学习者修改 Prompt。本项目将这部分拆进第 2 课的消息结构和第 6 课的结束原因、token 上限与 Eval。

和你刚遇到的问题直接相关： 你之前的 completion_tokens=100 刚好等于 max_tokens=100，而 finish_reason 是 length。这就是教程所说的“硬停止”：不是 Prompt 分类逻辑失败，而是生成额度先用完了。

本课程怎样处理旧内容

这套教程的部分模型名、SDK 字段和推荐实践已经不是最新版。本课程保留它的实验方法，并在第 7 课标出旧式思维链、XML 工具调用和 Assistant Prefill 等内容的现代用法。

4. OpenAI：把 Prompt 当成可测试的工程资产

OpenAI 的方法比较像生产手册。它不只问“这句 Prompt 怎么写”，还问：指令放哪里、优先级如何、模型升级怎么不引入回归、固定内容如何复用与缓存。本课程第 2、6、7 课完整展开这些工程问题。

4.1 消息角色是“权限层级”，不是 Prompt 技巧的名字

稳定的应用规则和当次用户输入应该分开。高优先级指令规定模型的目标、规则和输出约束；用户输入提供本次要处理的数据。它们是不同层次，不应全部糊成一个无边界字符串。

4.2 模型选择也是 Prompt 系统的一部分

不同类型和不同尺寸的模型，对指令显式程度、速度、成本和复杂推理的取舍不同。因此“同一 Prompt 在每个模型上都一样”不是可靠假设。生产应用应固定模型版本，并用 Eval 检查升级。

4.3 Few-Shot 的工程含义

文档将 Few-Shot 定义为：在 Prompt 中放少量输入/输出对，让模型拾取模式，而不是修改模型参数。它还特别建议范例要覆盖多样输入，不要只放三个几乎一样的容易案例。

4.4 上下文与 RAG

当答案依赖私有资料或特定来源时，要把相关上下文提供给模型。上下文不是越多越好：它受 context window 限制，而且无关内容会增加噪声。

4.5 为什么要将 Prompt 纳入代码版本管理

生产 Prompt 应作为应用代码的一部分进行版本控制、评审、测试和部署；动态值通过类型化变量或 schema 传入。对大量重复请求，稳定前缀放在前面还有利于 Prompt Caching。第 6 课会给出完整的实验和发布方法。

5. Google：给你一个可操作的策略工具箱

Google 的方法最适合“对着症状查策略”。核心观点是：Prompt Design 是迭代过程，要根据具体任务和实际输出反复实验。本课程已把这些策略分别放进第 2 至第 7 课。

5.1 它先把“输入”分成四类

输入类型模型在做什么例子
问题回答一个问题“为什么天是蓝的？”
任务执行一个动作“生成 5 个花店名字”
实体对给定对象操作“将这些动物分大/小”
补全继续你已经开始的模式给出 Output: 开头让模型续写

这个分类的价值是：当结果不对时，你可以问“我究竟是在提问，还是要求它做任务？”很多模糊 Prompt 混在一起了。

5.2 约束和输出格式要明说

模型不会自动知道你想要列表、表格、一句话还是 JSON。只说“帮我整理”是把格式选择交给模型。对简单格式，Prompt 可以规定；对需要机器严格解析的 JSON，应优先使用 Structured Outputs 或 schema，而不只靠自然语言。

5.3 Google 对 Few-Shot 的建议更强

文档强调范例可以控制格式、措辞、范围和整体模式，并建议使用具体、多样且格式一致的范例。但这不是“范例越多越好”：过多范例可能增加成本，也可能让输出过度贴合范例。最终数量必须由 Eval 决定。

5.4 复杂任务不一定靠一个超长 Prompt

Google 给出三种拆法：

  1. 拆指令：一个 Prompt 只处理一类任务，根据输入路由。
  2. 链式处理：上一步输出变成下一步输入。
  3. 并行后聚合：对资料的不同部分并行处理，最后合并。

这是从 Prompt Engineering 走向 Agent/Harness Engineering 的过渡：有些问题应该改流程，不是继续加长 Prompt。

5.5 参数也是实验变量

max output tokens、temperature、topP、topK 和停止序列会影响生成。但要避免一次同时改 Prompt 和参数，否则你不知道是哪个变量导致结果变化。

6. 把三份资料放回你的客服分类代码

你当前的 Prompt 已经可以映射到三家文档的共同方法：

目标：将客服留言分到 billing、bug 或 other。
资料：<input_data>{message}</input_data>
规则：只根据资料分类；不知道时选 other。

范例：
输入：信用卡又扣了一次
输出：billing
...

输出：只返回一个小写标签。
代码中的设计对应哪个概念
固定目标、规则和输出清晰指令与稳定 Prompt
{message} 每次替换指令与输入数据分离
三个输入/输出对Few-Shot 行为演示
只允许三个标签输出约束
六条 cases 自动评分Eval 和回归测试
检查 finish_reason把参数/截断问题与 Prompt 问题分开
