Lesson 06 · Engineering Loop

Prompt 不是文案，是需要回归测试的程序逻辑

这一课覆盖生成参数、Prompt 迭代策略、Fallback、版本化、缓存、模型升级和 Eval。目标是让你能证明一次修改是否真的变好。

1. 五个常见生成参数

参数影响常见误解
max_output_tokens允许生成的最大 token 数它不是期望长度，而是硬上限
temperature对候选 token 采样随机性的影响0 不代表跨环境、跨版本绝对确定
top_k只从概率最高的 K 个候选中选不是所有模型都支持或建议自定义
top_p从累积概率达到阈值的候选集采样不要与 temperature 一起无目的调整
stop_sequences出现指定字符串时停止生成序列如果会出现在正文中，就会误截断
参数是模型特定的。Google 当前文档说明：Gemini 4 和 Gemini 3.6+ 忽略自定义 temperature、top_p、top_k，并将逐步对这些配置返回错误；某些早期 Gemini 3 模型也建议保持默认，避免破坏推理。不能把老模型的调参经验直接套到新模型。

2. 先看结束原因，再怪 Prompt

choice = response.choices[0]
text = choice.message.content or ""

print("answer:", text)
print("finish_reason:", choice.finish_reason)
print("usage:", response.usage)

如果 finish_reason == "length"，说明输出额度先用完了。这时重写分类规则可能完全没有用。你之前的空响应正是这一类问题。

3. Prompt 迭代时可以改什么

  1. 重新措辞：用更直接、可检查的语言表达同一目标。
  2. 改成类似任务：例如将开放问答改成从有限选项中选择。
  3. 调整内容顺序：比较范例、上下文、当前输入的不同顺序。
  4. 补一个边界范例：针对已知错误，不要无目的加大量范例。
  5. 增加相关上下文：当问题是知识不足，而不是指令不清。
  6. 拆分流程：当单次 Prompt 同时承担太多任务。

迭代不是随意重写。每一次修改都应有假设：“如果错误是由 X 造成，那么只修改 Y 后，案例 Z 应该改正。”

4. 一次只改一个变量

如果同时换模型、改 Prompt、加范例、调 temperature，分数上升后你不知道原因。一个干净实验需要固定：

  • 模型名与模型版本
  • 生成参数
  • 测试题集
  • 正确答案与评分规则
  • 运行次数与随机性策略

然后只修改一处，重跑全部 Eval。

5. Eval 不只是总分

维度客服分类器的测量
任务正确性标签与标准答案一致
格式正确性只有三个合法小写标签
稳定性重复运行时不频繁改变
成本prompt/completion/reasoning token
延迟每次分类耗时
未知输入边界或信息不足时是否安全退回 other

总分 6/6 不代表已经足够好。如果六道题全部很简单，新旧 Prompt 都满分，就出现天花板效应：当前测试无法区分它们。

6. 生产环境要固定模型快照

同一模型家族的不同快照可能在指令遵循、格式和边界案例上有差异。生产系统应使用明确模型版本，升级时运行回归 Eval，而不是无声切换到“最新”。

7. Prompt 应放在代码和版本控制中

OpenAI 当前建议将生产 Prompt 保存在应用代码中，使用类型化参数/schema 提供动态值，并通过普通代码评审、测试、部署和特性开关发布。

def build_classifier_prompt(message: str) -> str:
    return f"""# Task
将留言分为 billing、bug 或 other。

# Input
<message>{message}</message>

# Output
只返回一个合法标签。"""

截至 2026-11-03，OpenAI 文档已标记 API 端可复用 Prompt Object 为废弃路线：2026-06-03 起弱化推广，v1/prompts 计划在 2026-11-30 关闭。已有 prompt ID/version 集成应迁移回代码管理。

8. Prompt Caching 与长上下文

反复使用的规则、工具定义和范例放在请求前缀，动态用户数据放在后面，可以提高 cache 命中机会。缓存主要优化成本和延迟，不会弥补不正确 Prompt。

模型只能在 context window 内处理输入、对话历史、工具结果和输出。即使上下文窗口很大，也应该做相关性筛选：“能塞进去”不等于“应该塞进去”。

9. Fallback 的两种含义

Google 页面将 Fallback Response 主要定义为安全过滤器触发后返回的拒答。原页建议在某些情况下增加 temperature，但这不是普适解法：

  • 如果是真正安全边界，不应用调参试图绕过。
  • 如果是误触发，应重写任务上下文、说明合法用途，并按当前模型文档处理。
  • 应用层的 Fallback 还应包括：超时、工具失败、解析失败和信息不足时的安全退路。
