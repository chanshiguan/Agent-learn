Lesson 03 · Output & Examples

不只要答对，还要让程序接得住

这一课将 Anthropic 的输出格式与 Few-Shot、OpenAI 的 Markdown/XML 结构、Google 的补全策略和范例一致性合成一套可操作方法。

1. 输出格式是任务契约

模型默认倾向“帮助人”，所以常会加前言、解释、Markdown 或客套话。人类可以看懂，但程序可能只接受一个标签。

人类可读

“根据留言内容，我认为这属于 billing。”

程序可解析

billing

格式要求应该具体到可检查：

  • 允许哪些值：billing、bug、other。
  • 是否允许解释：不允许。
  • 是否允许 Markdown：不允许代码块。
  • 大小写和空白如何处理：小写，无多余空白。

2. XML 和 Markdown 的真正作用

Markdown 标题适合表达层次，XML 标签适合标记数据边界和元数据。它们的作用是减少歧义，不是“提升智商”。

# Identity
你是留言分类器。

# Instructions
- 只使用留言中的信息。
- 不确定时输出 other。

# Input
<message id="case-17">我被扣款两次</message>

# Output format
只返回 billing、bug 或 other。

对简单文本提取，可以要求模型用 <answer>...</answer> 包裹关键结果，再由程序提取。对严格结构数据，应使用 Structured Outputs/schema，而不要把 XML 或“返回 JSON”当成硬保证。

3. 预填充：给模型一个已经开始的模式

Anthropic 旧教程将这种做法称为“替 Claude 先说一点”；Google 称为 completion strategy。思路是相同的：给出输出开头，让模型沿着模式继续。

任务：输出订单中存在的商品数量。
订单：两个汉堡和一杯饮料。
输出：
{

它可以减少前言并引导格式，但仍然不是有效 JSON 的硬保证。不同 API 对 assistant prefill 的支持也可能不同，必须查当前模型文档。

4. Stop Sequence：何时停止生成

如果预期结果以 </answer> 结束，API 可以配置该序列为停止条件，从而减少标签之后的多余内容。停止序列不能选择容易在正文中出现的字符串，否则会提前截断。

5. Zero-Shot、One-Shot 和 Few-Shot

方式范例数优势风险
Zero-Shot0短、快、成本低边界和格式可能不稳定
One-Shot1能演示一种理想格式一个范例可能让模型过度概括
Few-Shot少量展示多个边界与输出模式占用 token，坏范例会教坏模型

Few-Shot 不是微调。它没有修改模型参数，范例只在当前上下文中生效。

6. 好范例的四条标准

  1. 正确：输出必须是你真正想要的答案。
  2. 多样：覆盖不同类型和容易混淆的边界，不只是三个同类简单案例。
  3. 一致：标签、空格、换行、XML 和分隔符保持一样。
  4. 代表性：范例的分布要接近真实输入，并包含失败过的边界。
不要把“Google 建议经常使用 Few-Shot”理解成永远加范例。范例数没有固定答案。太多范例会增加上下文和成本，也可能让输出过度贴合范例。用 Eval 决定。

7. 指令和范例如何分工

指令适合表达通用规则；范例适合展示难以用话说清的边界、语气和格式。

# Instructions
- 扣款、支付、发票属于 billing。
- 界面或功能异常属于 bug。
- 其他请求属于 other。

# Examples
<example>
  <input>付款页面打不开</input>
  <output>bug</output>
</example>

这个边界范例很重要：它同时提到“付款”和“页面打不开”，因此能演示“技术故障优先按 bug 分类”的边界规则。

8. 稳定前缀与 Prompt Caching

对大量重复请求，将身份、规则和范例这些稳定内容放在前面，将每次变化的输入放在后面，有利于供应商的 Prompt Cache 命中。它不改变正确性，主要用来减少延迟和成本。
