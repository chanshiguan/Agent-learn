发布前先知道怎样退回来

给当前候选镜像一个不会覆盖旧版本的标签。选一份已验证旧版本与当前候选，不在运行中随意改源文件。程序和资料若不兼容，单换镜像无法完成回滚，数据库恢复要按下一章演练。

# 将当前 candidate 镜像标记为一个明确的练习版本；它不推送到任何远程仓库。
docker tag classics-companion:candidate classics-companion:trial-v1
# 使用该版本启动受控试用，仍只开放本机端口；不要加 --build 覆盖选定旧产物。
RELEASE_TAG=trial-v1 docker compose -f deploy/compose.yaml up -d --no-build
# 检查依赖就绪后，再人工做登录、问答、来源和笔记批准的冒烟检查。
curl --fail http://127.0.0.1:8000/readyz

新版本出问题时，停止接入新请求，保存失败 trace 和版本，切回上一已验证标签，再检查相同四条业务路径。当前还只有一个版本时，先制作并验证第二个候选，再练撤回；不要捏造一个不存在的“上个版本”。

小范围试用看什么

限制试用账号、资料与时间窗口，确认告警和联系人。收集问题后按严重程度处理：越权、错误副作用和无法恢复的数据问题先阻止扩大范围；普通表达改进可进入待办，但要有负责人。

回滚记录写原因、前后版本、开始结束时间、数据是否变化、复测结果。仅把容器重新启动不等于回滚。

先遮住答案，回答下面的问题，再核对自己的运行记录。

  1. 为什么回滚可能还涉及资料与数据库？
  2. 只有一个镜像能完成回滚演练吗？
查看参考答案与通过标准

为什么回滚可能还涉及资料与数据库？

旧程序可能读不懂新结构，旧 Prompt 也可能依赖旧资料字段。必须验证版本组合，必要时恢复兼容快照。

只有一个镜像能完成回滚演练吗？

不能证明版本切换。先保留并验证两个明确产物，再实际切回并复测。

**通过证据：**两份真实版本的切换与回退记录，以及四条业务冒烟检查。

下次开始前

隔一天，先不看命令，解释本单元解决了什么问题，以及哪种情况仍会失败。再用你自己的一个阅读问题重跑关键步骤。若卡住，带上单元名称、预期结果和去掉凭据的错误信息继续讨论。
